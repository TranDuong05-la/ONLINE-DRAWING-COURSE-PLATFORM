## Schema and transaction facts

V1–V7 in `src/main/resources/db/migration/` define the integrated tables:

- V1: `users`, `user_profiles`, `user_addresses` (A/Auth plus D profile/address schema).
- V2: `carts`, `cart_items`.
- V3: `orders`, `order_items`, `order_shipping_addresses`.
- V4: `vouchers`, `voucher_user_usage`, `voucher_claims`.
- V5: `payment_attempts`, `payment_events`, `payment_event_conflicts`.
- V6: `carts.revision` and its nonnegative check.
- V7: `checkout_requests` with `(user_id,idempotency_key)` uniqueness, optional unique Order FK, and PROCESSING/COMPLETED consistency checks.

No Course, Enrollment, Product, stock, inventory reservation, shipment, refund, or outbox table is defined in these migrations. Existing cart/order item `item_id` columns are polymorphic IDs, not foreign keys to missing catalogs. A single ACID transaction is feasible only if B/C/E adapters use this same MySQL datasource, schema, and transaction manager. The repository provides one datasource/transaction manager; module sharing is unverified.

The future Checkout transaction must not invoke `CartApplicationService` or Order/Payment `REQUIRES_NEW` read operations. It should use repositories directly and `OrderPersistenceService.insertNew`/`CheckoutIdempotencyService` REQUIRED participation. The current services are explicitly constructed/unwired except the pending-purchase component and persistence repositories; no Checkout bean composition exists. The Cart endpoint remains conditional and lacks production composition.

## Proposed Checkout transaction flow

1. Resolve the Integer owner from `AuthenticatedUserIdResolver`/the existing trusted Order identity adapter. Reject any client owner ID or price field.
2. Parse and validate `Idempotency-Key` (1–64 characters) and the bounded Checkout request. Build the current canonical fingerprint from the supplied Cart revision, selections/quantities, stripped voucher code and normalized address.
3. In one REQUIRED transaction, call `CheckoutIdempotencyService.claim` **before reading/comparing the current Cart revision**. Return the owner-scoped original Order for `Replayed`; map fingerprint mismatch and in-progress/race to documented conflicts. A race exception requires rollback and retry.
4. Lock the owner's Cart with `CartRepository.findByUserIdForUpdate`; require its persisted revision to match the request. Validate each selected Cart item belongs to this Cart, the selection is nonempty, unique, and quantity matches the locked Cart contents. Partial selection is allowed; do not mutate Cart until a separate agreed rule says so.
5. Read trusted B/E offers and revalidate active/purchasable states and current prices. Reject missing/inactive items. Recheck C ownership and the D active-pending query for selected Courses. Fetch authoritative E stock; Cart display subtotal/status is not trusted.
6. Acquire provider locks/claims in a globally agreed, deterministic order (sort Course IDs and Product IDs; then lock voucher definition and per-user usage). Revalidate mutable facts under those locks. Do not hold database locks across remote HTTP calls.
7. Validate voucher against current campaign window, activation, minimum eligible merchandise, and total/per-user capacity. Apply it only to eligible COURSE/PRODUCT lines, not shipping. Use `OrderDiscountAllocator`; never recalculate later. Obtain a trusted shipping quote if required and freeze the fee and supplied address snapshot.
8. Construct the immutable `Order` snapshot with trusted catalog values and the fixed 30-minute exclusive deadline. Persist it inside this transaction to obtain its Integer ID. This ordering is needed because `VoucherClaim.reserved(...)` requires both the persisted Order ID and the Order snapshot; if C/E reservation APIs also require an Order ID, they can be called now while the new Order remains uncommitted.
9. Atomically reserve E stock, claim C Course purchases, increment voucher definition/user reserved counters, and insert the voucher claim snapshot, all within the same local transaction. If any claim/reservation fails, roll back the Order, all reservations/counters, and idempotency claim together. Providers must make their operations idempotent for an Order and preserve deterministic lock order.
10. Complete the idempotency row with the owner-checked Order ID using `CheckoutIdempotencyService.complete`; commit the local transaction. Do not initiate a payment gateway call before this commit.
11. Only after commit, prepare/return a payment session through a separate payment operation. A gateway session is not atomically committed with MySQL; define retry and reconciliation behavior independently. Late or ambiguous success must be reconciled, not treated as fulfillment.

**Lock-order decision required:** Checkout and future cancellation/settlement flows must agree on one resource lock order. A workable proposal is (a) Checkout idempotency key; (b) Checkout Cart row; (c) existing Order row first for Order transitions; (d) Course claim rows ordered by Course ID; (e) Product inventory rows ordered by Product ID; (f) voucher definition, then voucher/user-usage rows ordered by ID. New Order insertion is not a contended row. Every flow acquiring more than one shared C/E/voucher resource must preserve the same relative order. Confirm with B/C/E before implementation; their actual locking/storage is not present here.

## Main blockers and risks

- **B:** no trusted Course catalog adapter or confirmed purchase eligibility semantics.
- **C:** no ownership implementation or atomic Course purchase claim/confirm/release operation. The current pending-order query alone permits a concurrent double-check race.
- **E:** no trusted Product adapter, stock source, atomic reserve/release/confirm, or shipping quote implementation.
- **Voucher:** definitions/claim records/counters and pure transitions exist, but no transactional validator/reservation coordinator. Campaign changes after a successful reservation must not invalidate that Order's stored claim snapshot.
- **Payment:** attempts/events are persistence/audit primitives only. No verifier/controller/settlement coordinator transitions the Order, redeems/releases voucher, or confirms/releases C/E claims.
- **Idempotency:** V7 is available and H2-tested, but MySQL verification is separate. Future caller must keep claim, Order, all local reservations, and idempotency completion in one transaction; a caller that commits a PROCESSING claim separately would violate the implemented service contract.
- **External payment:** gateway work cannot be transactionally atomic with local Order/claims. A post-commit retry/reconciliation contract is needed before enabling payment initiation.
- **Schema ownership:** any C/E tables/constraints must come from those members' actual schema proposals. Do not infer them from the conceptual DBML or introduce parallel ownership/inventory ledgers.
